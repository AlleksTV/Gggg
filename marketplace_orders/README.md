# Тема 2. Система управления заказами и складскими остатками

Python + FastAPI (Swagger) + SQLAlchemy + PostgreSQL.

Главное в проекте: оформление заказа как одна ACID-транзакция, защита от гонки,
когда два человека одновременно покупают последний товар, и автоматическое снятие
неоплаченного резерва по таймауту.

## Как запустить (Windows)

1. Установите **Python 3.11+** и **PostgreSQL 16**. При установке PostgreSQL задайте пароль `postgres`.
   Если установлен Docker, вместо PostgreSQL можно выполнить `docker compose up -d`.
2. Создайте базы. Это можно сделать в pgAdmin или в консоли `psql -U postgres`:
   ```sql
   CREATE DATABASE marketplace;
   CREATE DATABASE marketplace_test;
   ```
3. В папке проекта выполните:
   ```bat
   python -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt
   python -m app.seed
   python -m uvicorn app.main:app --reload
   ```
4. Откройте **http://127.0.0.1:8000/docs**. Это Swagger, где все методы можно вызывать прямо из браузера.

Если у PostgreSQL другой пароль или порт, перед запуском задайте адрес базы:
`set DATABASE_URL=postgresql+psycopg://postgres:ПАРОЛЬ@localhost:5432/marketplace`

### Демонстрация гонки

```bat
python demo_race.py
```

## Модель БД

| Таблица | Назначение |
|---|---|
| `users` | Покупатели |
| `warehouses` | Склады (FBO / FBS) |
| `skus` | Товары с ценой |
| `stocks` | Остаток SKU на складе: `quantity` (всего), `reserved` (в резерве), `version` |
| `orders` | Заказ: статус, сумма, срок оплаты `reserve_expires_at` |
| `order_items` | Позиции заказа (цена фиксируется на момент покупки) |
| `reservations` | Резервы товара под заказ: `active` → `consumed` / `released` |
| `stock_movements` | Журнал движения товара: `income`, `reserve`, `unreserve`, `outcome` |
| `order_status_history` | История смены статусов заказа |

Доступно к продаже: `quantity - reserved`.

На уровне БД стоят ограничения `CHECK`: `quantity >= 0`, `reserved >= 0`, `reserved <= quantity`.
Даже если в коде будет ошибка, база не позволит уйти в минус.

**Event Sourcing на минималках.** Таблицы ничего не удаляют и не переписывают задним числом.
Каждое изменение остатка пишется новой строкой в `stock_movements`, каждая смена статуса
пишется строкой в `order_status_history`. По журналу всегда можно восстановить, что
происходило с товаром и заказом.

## Жизненный цикл заказа

```
reserved ──оплата──> paid ──> assembling ──> shipped ──> delivered
   │                  │
   ├──отмена──> cancelled <──┘
   └──таймаут──> expired
```
Недопустимые переходы, например `reserved → shipped`, запрещены (`ALLOWED_TRANSITIONS` в `services.py`).

## Алгоритмы

### 1. ACID-транзакция при оформлении заказа
Проверка остатков, резерв, создание заказа, позиций, резервов и записей в журналах выполняются
в **одной транзакции** (`with session.begin():`). Если хоть одного товара не хватает,
откатывается всё. Например, корзина «кроссовки + 100 ноутбуков» не зарезервирует даже
кроссовки (тест `test_order_is_atomic_when_one_item_missing`).

### 2. Проблема: состояние гонки (Race Condition)
```
Покупатель А: читает остаток = 1 ─┐
Покупатель Б: читает остаток = 1 ─┤  оба видят «есть 1 шт.»
Покупатель А: записывает резерв  ─┤
Покупатель Б: записывает резерв  ─┘  товар продан дважды
```
Функция `create_order_unsafe` специально написана так, чтобы показать эту проблему.

### 3. Пессимистическая блокировка: `SELECT ... FOR UPDATE`
```sql
SELECT * FROM stocks WHERE sku_id = 3 ORDER BY warehouse_id FOR UPDATE;
```
Строки остатка блокируются **до** проверки. Второй покупатель ждёт на этом `SELECT`,
пока первая транзакция не завершится, и затем видит уже уменьшенный остаток.
«Пессимистическая» значит, что мы заранее считаем конфликт вероятным и сразу ставим блокировку.

**Защита от deadlock.** Товары в корзине сортируются по `sku_id`, поэтому все транзакции
блокируют строки в одном и том же порядке и не могут ждать друг друга по кругу.

### 4. Оптимистическая блокировка: поле `version`
```sql
-- прочитали остаток и version = 7 без блокировки
UPDATE stocks SET reserved = reserved + 1, version = version + 1
WHERE warehouse_id = 2 AND sku_id = 3 AND version = 7;
-- изменено 0 строк -> кто-то успел раньше -> откат и повтор
```
Ничего не блокируется. Если при записи `version` уже другой, строку изменил кто-то другой:
транзакция откатывается и повторяется заново, до 10 попыток с небольшой паузой.
Этот способ хорош, когда конфликты редкие.

| | Пессимистическая | Оптимистическая |
|---|---|---|
| Когда проверяем конфликт | До изменения (блокируем) | При записи (сверяем version) |
| Что делает второй | Ждёт | Откатывается и повторяет |
| Лучше подходит | Частые конфликты (горячий товар, распродажа) | Редкие конфликты |

### 5. Автоматическое снятие неоплаченного резерва по таймауту
При оформлении заказ получает срок оплаты `reserve_expires_at` (по умолчанию 15 минут).
Фоновая задача в `app/main.py` раз в 10 секунд выполняет:
```sql
SELECT * FROM orders
WHERE status = 'reserved' AND reserve_expires_at <= now()
FOR UPDATE SKIP LOCKED;
```
Для найденных заказов резерв возвращается в доступный остаток, статус меняется на `expired`.
`SKIP LOCKED` пропускает заказы, которые прямо сейчас кто-то оплачивает, поэтому фоновая
задача не конфликтует с оплатой. Если покупатель пытается оплатить уже просроченный заказ,
оплата отклоняется и резерв снимается сразу.

Проверить в Swagger: создайте заказ с `"reserve_seconds": 5`, подождите 10–15 секунд и
откройте `GET /orders/{id}`. Статус будет `expired`. Можно не ждать фоновую задачу
и вызвать `POST /admin/expire-reservations`.

## Демо-данные (`python -m app.seed` или `POST /admin/reset`)

| SKU | Товар | Остатки |
|---|---|---|
| 1 | Кроссовки | склад 1: 10 шт., склад 2: 5 шт. |
| 2 | Ноутбук | склад 1: 3 шт. |
| 3 | Футболка | склад 2: **1 шт.** (для гонки) |

Пользователи: 1, 2, 3.

## Пример запроса в Swagger
`POST /orders`
```json
{
  "user_id": 1,
  "items": [{"sku_id": 1, "quantity": 2}, {"sku_id": 2, "quantity": 1}],
  "lock_mode": "pessimistic"
}
```
`lock_mode` принимает значения `pessimistic`, `optimistic` или `unsafe` (последнее только для демонстрации).
